# SkillRoster 首次使用体验检查

检查日期：2026-10-15（Asia/Taipei）。

以下记录实施前的产品检查及其依据。用户随后选择同时改进全部五项；本文末尾记录候选版的实现和验收，原始观察保留用于比较。

## 检查范围

- 当前主线：`c76607a0e58aef03fb293ccab8ad171f3a5ede74`，通过 `cargo build --locked` 构建。
- 公开版本：[v1.8.45](https://github.com/tt-a1i/skillroster/releases/tag/v1.8.45)，下载并验证 macOS arm64 包；SHA-256 为 `cc6f0b89a49a3dcd2e6df56af6384640a6210e5e474d299be299f6e2b421c2c0`，与相邻校验文件一致。
- 两个版本分别使用独立的临时 Home 和 state 目录，执行 Home、Scan、Report、Finding 下钻、Setup 预览和治理 Plan 预览。检查的是 CLI 和 Agent JSON 合同，没有用真实用户会话衡量理解成本。
- 公开包通过现有 `scripts/release/smoke.sh`：只在合成目录中执行 Bootstrap Apply、Undo 和恢复检查。产品体验场景中的治理 Plan 均停留在预览。

四个场景在两个版本中都成功返回结果：

| 场景 | 构造 | 当前主线观察 |
| --- | --- | --- |
| 空环境 | 没有 Skill、Agent 目录或会话 | 0 个 Skill，3 条信息性 Finding，29 行终端报告 |
| 小目录 | 3 个带来源、版本和不同能力描述的 Skill，没有会话 | 4 条信息性 Finding，30 行终端报告 |
| 重复副本 | 上述目录，加一个跨 Agent 相同副本和一个指向批准范围外的失效链接 | 首屏包含链接边界、精确重复和路由元数据问题；重复副本可生成有效 Plan |
| 大目录 | 55 个 Skill，没有使用记录 | 默认方案保留 50 个 Core；50 个均来自名称和稳定 ID 排序 |

大目录中的 52 个合成 Skill 使用相似描述，因此语义重叠数量只用于检查输出行为，不代表真实库的重叠率。

## 1 让空环境和暂不需要整理的环境有明确终点

**观察。** 空环境仍将 `Archive candidacy is unknown`、`Five-stage usage evidence` 和 `Usage coverage is incomplete` 列为 Top Findings。三个正常 Skill 的首屏也主要是信息不足说明。信息都是真实的，但用户仍要判断“这些是不是需要修的问题”。

**建议。** 先按已观察到的事实区分“没有发现 Skill”“发现可处理问题”“目前没有明确整理项”。空环境说明查过的范围，保留补充目录入口；小目录可以建议保持现状。使用覆盖不足保留为一条限制说明，下钻仍能查看完整事实。不要为了满足“Top 三条”而补齐问题，也不要把未知说成健康或无用。

**预期首屏示例。**

> 找到 3 个 Skill，目前没有发现重复副本或链接问题，可以保持现状。
> 没有可用的使用记录，因此这次不判断哪些 Skill 用得少。

**验收。** 空环境没有整理或归档建议；小目录能在首屏结束；损坏、歧义、不完整扫描仍明确显示，完整 JSON 和 Finding 可追溯性不丢失。

## 2 把已有事实组织成一个可选择的小方案

**观察。** Report 已返回 `actionability` 和 `reversibility`，精确重复 Finding 也已有候选源和 Plan 模板。实际合成 Plan 能把相同内容的物理源从 2 份变成 1 份，同时保持两个 Agent 的暴露数 2→2、无 canonical 删除。能力已经具备，但终端主要展示 `observed → managed`、`create_symlink` 等操作，Report 的后续动作列表先提供继续枚举。

**建议。** 调用 Agent 用已有事实说明“哪两份相同、保留哪份、另一份会怎样、两个 Agent 是否还能用、如何撤销”，给出“预览这个整理方案”和“保留现状”。原始术语和操作明细保留供审查，不要求用户先理解整个领域模型。动作列表是选项，不能把数组顺序当成业务优先级，也不能替用户选择同名异内容的 canonical。

**预期方案说明。**

> Codex 和 Claude 各有一份相同的 review Skill。
> 这份预览保留 Claude 目录中的内容，将 Codex 的副本换成链接。两个 Agent 仍能使用，物理源 2→1，默认暴露保持 2，操作可撤销。

这是合成场景中的指定选择，不是按 Agent 名称自动选择来源的规则。

**验收。** 看完首屏即可回答改什么、为何改、影响谁、能否撤销；before/after 数字来自实际 Plan；只有分析请求时不创建治理 Plan。

## 3 分清命令已安装和 Agent 已接入

**观察。** README 的快速开始在安装 CLI 后直接让用户向 Agent 提问；Bootstrap 安装说明在另一页。小目录完成 Scan 和 Report 后，Home 显示 `ready` 和 `No required continuation`，此时 Setup 仍发现一个缺失的 Bootstrap。

**建议。** 保持 CLI 可独立使用，同时在首次引导中说明两种状态：“命令可用”和“当前 Agent 的引导 Skill 已就绪”。选择通过 Agent 使用时才引导预览 Setup，展示将影响的 Agent 和文件。不要把所有支持的 Agent 都自动接入，也不要为了显示状态悄悄 Apply。

**验收。** 新用户按快速开始能知道是否需要接入；已完成接入者不被反复引导；普通命令行使用不因缺少 Bootstrap 被阻止。

## 4 把常驻能力的选择交还给使用者

**观察。** 在没有会话证据的 55-Skill 场景中，默认 Plan 为 55→50，50 个 Core 全部是 fallback。主线已经正确披露 `name_then_stable_id_not_usefulness`，并提供 upcoming-work 提问和 `protected_skill_ids`；这些机制无需再造。

**建议。** 当缺少正向使用证据时，先在 Agent 对话中确认用户要解决的是重复副本还是默认列表太长。后者再确认接下来工作所需的常驻能力；信息不足时保留当前 Roster。把“按名称生成的可审阅草案”和“有使用证据的选择”直接说清，不将数量下降包装为效果改善。

**验收。** 用户只要求整理重复时不顺带减少 Core；用户拒绝精简也是完整结果；选择原因和未知项在摘要中可见。

## 5 让安装得到的产品对应当前承诺

**观察。** 公开包的 Bootstrap 是 1.8.29，主线是 1.8.49，两个 CLI 都显示 1.8.45。主线中的普通任务可继续执行、Claude 本地可见性和 Finding 决策信息尚不在该公开包中。这一差异已写入安装文档，但快速开始读者不容易意识到。

**建议。** 下一次发布前，用同一公开安装路径验证版本、Bootstrap 和首次检查。产品说明明确已发布行为；主线能力在正式交付后再成为默认预期。版本检查需要同时看 executable 和 Bootstrap，不能只凭 CLI 版本号判断。

**验收。** 新安装用户无需切主线或手动替换 Skill，便能走完说明中的流程。发布仍需独立的产物和平台验证。

## 建议执行顺序

先实现第 1、2 项的首屏和 Agent 呈现改进，保留全部底层事实与安全门槛；然后补第 3 项的接入指引。第 4 项优先复用现有用户选择机制，第 5 项作为交付检查。

这轮不需要新增排序器、模型调用、偏好系统或 GUI。下一次检查用相同四个场景确认：首屏是否说清现状，是否有一个合理的下一步，何时可以放心结束。
